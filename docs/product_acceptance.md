# 产品验收闭环

本文是 `project_template_go` 及其实例的产品验收规范，与 xjb_coding 项目约束 [产品验收闭环](https://github.com/0xdevelop/xjb_coding/blob/latest/skills/xjb-coding/references/product-acceptance.md) 为同一套要求。实例应遵循本文，不要另写一套互不引用的手册。根 README 只保留短说明并相对链接到本文或后续实测记录。

本规范是强制项目约束，不是可选建议。过程增强（联动补强、隔离回退、复用已有环境的试跑、本地打包验证等）只是过程证据，不是最终预期。最终预期是第 1 节闭环全部实际走通。

本文是内部操作规范，不进入对外 API 文档页（`docs` 包只 embed `api_methods.md`）。

## 1. 验收闭环（必须全部实际发生）

产品验收通过，当且仅当下列步骤都已在目标环境**实际发生**，并且根目录 `docs/` 留下对应实测文档：

1. **从 GitHub Release assets 下载**对应架构的发布包。必须使用该 Release 的资产 URL。禁止用本地 `build/`、打包目录、手工拼装的半套包或其他非 Release 产物冒充 GitHub assets 验收。
2. **用本项目官方安装脚本**部署到**脚本写明的根目录**。本模板脚本为 `example_files/install_project_template_go.sh`（实例化后文件名随项目名替换），安装根目录为 `/${APP_NAME}`（本模板即 `/project_template_go`）。禁止自行改安装前缀，禁止改装到 `~/.local/share` 或其他未由官方脚本指定的路径。
3. **systemd 服务启动**成功。单元安装到 `/etc/systemd/system`，名称与脚本声明一致（本模板为 `project_template_go.service`）。
4. **跑完全程并得到预期业务结果**。所宣称的任务、步骤、产物必须真实发生并可核对（路径、哈希、日志、查询结果等）。
5. **按官方脚本卸载**（同一安装脚本的 uninstall 选项），并核对服务已停止、单元已移除、`/${APP_NAME}` 已按脚本清理。
6. **在项目根 `docs/` 留下详细测试过程文档**；根 README 只保留短说明并使用相对链接。

缺任一步，或某步只是计划、演练稿、局部测试、复用旧环境的结果，都不能把产品验收标为通过，也不能把实现进度写成 `ACCEPTED`。编译、单元测试、协议层测试和 `AutoMigrate` 成功是不同证据，不得与本闭环互相替代。

## 2. 发版底稿（禁止擅自重设计）

实例必须以本模板的 `git_tag.sh`、`build.sh` 和 GitHub Actions 三段发版为底稿，复制后只做必要的小幅增量适配，禁止重新设计入口、默认语义或生命周期。

- 无参 `./git_tag.sh` 是既有发版入口（脚本亦接受 `auto`，与无参走同一路径）。它会递增版本、生成文档、提交并推送**轻量 tag**。禁止把无参改成默认只读、另加 `--publish` 才发布、把默认轻量 tag 改成附注 tag，或把交互式 `custom` 变成默认入口。不要改本模板的 `git_tag.sh` 契约来迁就某个实例。
- `build.sh` 由 Actions 的 Build 作业调用（本模板为 `bash ./build.sh` 与 `bash ./build.sh test`），负责构建与打包。
- `.github/workflows/release.yml` 保持三段顺序：`release` → `Build` → `RemoveOldRelease`。禁止重排、拆掉或改掉原有清理行为。模板里移动 `latest`、清理旧 Release/tag 的行为按原样保留；需要实际执行这些清理时按脚本与工作流进行，不在工作流外擅自补做或取消。

允许的增量适配仅限有依据的项目差异，例如额外产物、原生多架构 runner、CGo / 实际 Go 版本、全部包校验通过后再上传。这些适配不能成为改掉上述契约的理由。

无参 `./git_tag.sh` 会推 tag 并触发上述三段，未获授权不要执行。发版本身不等于产品验收通过；必须等到 Release 资产可下载之后，再按第 1 节做正式安装与业务验收。

## 3. 测试过程文档

实测文档放在项目根 `docs/`（例如 `docs/acceptance_<date>.md`），并在根 README 用相对路径做短链。必须记录实际发生的内容，至少包括：

- 实际执行的步骤与命令；
- 实际发生的时间，并标明时区（禁止把计划时间写成发生时间）；
- Release 页面与 asset 的 URL、资产名称、校验和（若有）；
- 官方安装脚本路径、脚本写明的安装根目录、实际安装路径、systemd 单元名与启动结果；
- 任务、步进、产物等业务事实（路径、哈希、查询或日志摘录）；
- 官方卸载的命令或选项、卸载后的核对结果；
- 未覆盖项与限制（例如未做的架构、未授权的外部依赖、科学质量未验证等）。

禁止把计划写成已发生。禁止伪造业务结果。禁止在未做相应验证时，把预测或实验结果的科学质量写成已获验证。

L1 编译测试全绿、本地构建包、隔离夹具、复用已有环境的试跑，都可以作为过程证据写入文档，但必须标明范围，不能替代本闭环，也不能写成「已从 GitHub assets 完成正式安装验收」。

## 4. 提交、入口与执行纪律

- 提交作者只记录人类用户本人；禁止任何协作者信息，包括 AI / Cursor / `Co-authored-by` 及其他 agent 标识。提交后核对完整 message。禁止 force-push（含 `--force` 与 `--force-with-lease`）。已推送历史不擅自改写。
- 操作说明与实测过程写在根 `docs/`；README 只做短说明和相对链接。
- 只精确添加本任务文件；不把 `.auto_coding/` 工作区提交进 git。
- 不打印、不改写受保护配置与秘密。
- 执行者按已明确标准自行核对每一步证据，不把用户当验证者，不靠反复确认推进已明确的工作。仅在缺少用户才能提供的硬授权或凭据（例如尚未授予的发版、正式安装、部署凭据）时停止，并说明缺的是哪一项。

使用 xjb_coding 时，本闭环由该 Skill 的 `start_coding.md` 四层门禁 L4 与 §9 项目特定约定区强制引用；未在约定区填写安装路径也不能使本规范失效。
